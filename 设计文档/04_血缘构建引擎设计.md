# SQLineage 血缘构建引擎设计

> 版本: v1.0 | 模块: `lineage_engine` | Python

---

## 1. 引擎定位

血缘构建引擎是 SQLineage 的核心模块，负责将一段 SQL 查询解析为字段公民节点 + 子查询公民节点，并织入全局 DAG。

**输入**: SQL 文本 + 可选 sink 表名  
**输出**: `(new_fields: list[FieldNode], new_subqueries: list[SubqueryNode], field_references: list[Edge])`  
**特性**: 内容寻址，幂等，失败即回滚（事务边界）

---

## 2. 整体流水线

```
SQL 文本
  ↓
[Phase 0] 入参校验        — LIMIT / JOIN 规范 / 表存在性
  ↓
[Phase 1] sqlglot 解析    — 文本 → AST
  ↓
[Phase 2] AST 标准化       — CNF / 排序 / 谓词下推 / projection 下推 / in→join
  ↓
[Phase 3] 递归构建字段     — AST 自底向上递归
  ↓
[Phase 4] 构建子查询       — 从字段 hash 集构建子查询节点
  ↓
[Phase 5] 绑定 sink 表     — 更新 tables.input_subquery_hash + table_columns.field_hash
  ↓
[Phase 6] 写入事务提交
```

---

## 3. 逐 Phase 详细设计

### Phase 0 — 入参校验

在进入 sqlglot 解析前完成的轻量校验：

```
1. SQL 文本非空
2. (扫描) 是否包含 LIMIT 关键字 → 若存在，报 49001
3. (sqlglot parse 试解析) → 若语法错误，报 49002
4. (遍历 AST 中所有表引用)
   ├─ 是否为实体表 → 查 tables 表，不存在 → 报 49003
   ├─ 若表 source = root → 标记为 root 表引用
   └─ 若表 source = middle → 标记为 middle 表引用
```

**JOIN 校验规则**: RIGHT/FULL JOIN 由 Phase 2 normalizer 前置转换为 LEFT JOIN 或 UNION，不进入 Phase 0 校验。连续 INNER JOIN 和 INNER+LEFT 混合均已放开，不做限制。

**表引用提取**: 从 AST 中识别所有 `Table` 节点，收集 `(schema, table)` 对。子查询别名 (如 `AS tb_b`) 不在此列。

---

### Phase 1 — sqlglot 解析

```python
import sqlglot
ast = sqlglot.parse_one(sql, dialect="mysql")  # 先以通用方言解析，后续可扩展
```

结果是一个 sqlglot `Expression` 树，包含 `Select`, `From`, `Join`, `Where`, `Group`, `Order` 等节点。

**方言策略**: 默认使用 MySQL 方言（最宽松），后续支持用户选择 spark/hive/presto/postgres 方言。

### Phase 2 — AST 标准化

在构建字段节点之前，对 AST 做代数变换，使表达形式统一、可内容寻址。

标准化分两层：**sqlglot 内置优化器**处理大部分变换；**自研逻辑**补 sqlglot 不覆盖的部分。

#### 2.1 sqlglot 内置优化器 — 直接调用

从 `sqlglot.optimizer` 中选择性使用以下 pass（按推荐顺序）：

| Pass | 作用 | 启用 |
|---|---|---|
| `qualify` | 字段名补全：`mchnt_cd` → `table.mchnt_cd`（需提供 schema dict） | ✅ |
| `normalize` | CNF 标准化：`(A AND B) OR C` → `(A OR C) AND (B OR C)` | ✅ |
| `pushdown_projections` | 裁剪子查询中未被外层引用的列 | ✅ |
| `pushdown_predicates` | 谓词下推：外层 WHERE 推进子查询 | ✅ |
| `simplify` | 常量折叠 / De Morgan / 去括号 / 冗余简化 | ✅ |
| `optimize_joins` | JOIN 重排 — **禁用**，会破坏语义分析 | ❌ |
| `unnest_subqueries` | 子查询展平 — **禁用**，子查询是独立公民 | ❌ |
| `merge_subqueries` | 子查询合并 — **禁用**，同上 | ❌ |
| `eliminate_subqueries` | 消除子查询 — **禁用** | ❌ |
| `eliminate_joins` | 消除无用 join — **禁用** | ❌ |
| `eliminate_ctes` | 消除未引用 CTE — **禁用**，保留完整语义结构 | ❌ |
| `canonicalize` | 类型转换标准化 — 可用，副作用小 | ✅ |
| `annotate_types` | 类型推断 — canonicalize 的前置依赖 | ✅ |

**调用代码**:

```python
from sqlglot.optimizer import optimize

schema_dict = build_schema_from_tables()  # 从 tables + table_columns 构建
# schema_dict = {"trans_flow": {"mchnt_cd": "VARCHAR", "trans_at": "DECIMAL"}, ...}

normalized_ast = optimize(
    sql,
    schema=schema_dict,
    rules=[
        "qualify",
        "annotate_types",
        "normalize",
        "pushdown_projections",
        "pushdown_predicates",
        "canonicalize",
        "simplify",
    ]
)
```

#### 2.2 自研逻辑 — 补 sqlglot 不覆盖的部分

| 变换 | 说明 | sqlglot 为何不覆盖 |
|---|---|---|
| **CNF 子句排序** | AND/OR 内部子句按字典序排列，保证语义等价→hash 一致 | sqlglot normalize 转 CNF 但不排序 |
| **可交换运算排序** | `+` `*` `eq` `AND` `OR` 的左右操作数在字段构建后按子节点 hash 排序 | sqlglot 无此能力 |
| **in → join** | `WHERE x IN (SELECT y FROM t)` → `JOIN (SELECT DISTINCT y FROM t) ON x=y` | sqlglot 的 unnest 策略不同，且我们禁用了 |

**CNF 子句排序**（在 `normalize` 之后执行）：

```python
def sort_cnf_clauses(ast):
    """对 AND/OR 节点的子句按 sql() 字典序排列"""
    if isinstance(ast, (exp.And, exp.Or)):
        # 先递归排序子句
        for arg in ast.args.values():
            sort_cnf_clauses(arg)
        # 扁平化 + 排序 + 重建
        clauses = list(ast.flatten())
        clauses.sort(key=lambda e: e.sql())
        # 按原 op 重建
        ...
```

**可交换运算排序**（在字段构建阶段执行，见 Phase 3.4）：

```
build_expression(node):
    先构建所有子节点 hash
    如果 op 是可交换的（+, *, eq, AND, OR）:
        按子节点 hash 排序后再构建 expression
```

#### 2.3 标准化原则

- 化简优先，不引入信息损失
- 标准化后的 AST 作为 field/subquery hash 计算的输入
- sqlglot 覆盖不了的由自研补，保持"标准化→hash"链路完整

### Phase 3 — 递归构建字段

这是引擎的核心——自底向上遍历标准化后的 AST，为每个表达式子树生成字段节点。

#### 3.1 主递归函数

使用 sqlglot 原生 Expression 子类进行类型分派：

```python
import sqlglot.expressions as exp

def build_field(node: exp.Expression, context: BuildContext) -> str:
    cache_key = node.sql()  # 标准化后的 sql() 作为缓存键
    if cache_key in context.cache:
        return context.cache[cache_key]

    if isinstance(node, exp.Literal):
        result = build_literal(node, context)
    elif isinstance(node, exp.Column):
        result = build_column(node, context)
    elif isinstance(node, (exp.Binary, exp.Unary)):
        result = build_expression(node, context)
    elif isinstance(node, exp.Case):
        result = build_case_when(node, context)
    elif isinstance(node, exp.Join):
        result = build_join_field(node, context)
    elif isinstance(node, exp.Alias):
        result = build_alias(node, context)
    elif isinstance(node, exp.Anonymous):
        result = build_function(node, context)  # agg / lateral / get_json_object 等
    elif isinstance(node, exp.Select):
        result = build_subquery_select(node, context)
    elif isinstance(node, exp.Union):
        result = build_subquery_union(node, context)
    else:
        raise UnsupportedExpression(type(node).__name__)

    context.cache[cache_key] = result
    return result
```

**sqlglot 类 → 处理函数映射**:

| sqlglot 类 | 处理函数 | 说明 |
|---|---|---|
| `exp.Literal` | `build_literal` | 数字 / 字符串 / NULL / Boolean |
| `exp.Column` | `build_column` | `table.column` 或裸 column |
| `exp.Binary` | `build_expression` | `Add Sub Mul Div EQ NEQ GT LT GTE LTE And Or ...` |
| `exp.Unary` | `build_expression` | `Not Neg` |
| `exp.Case` | `build_case_when` | CASE WHEN ... THEN ... END |
| `exp.Join` | `build_join_field` | 所有 join 类型 |
| `exp.Alias` | `build_alias` | `expr AS name` |
| `exp.Anonymous` | `build_function` | 聚合(Sum/Count/Avg) / get_json_object / nvl 等 |
| `exp.Window` | `build_window` | `func() OVER (PARTITION BY ...)` |

#### 3.2 `build_literal` — 字面量

```
expression = {"op": "literal", "value": str(node.this), "type": infer_type(node)}
hash = sha256(canonical_json(expression))[:16]
→ UPSERT field(hash, type='literal', expression)
→ return hash
```

#### 3.3 `build_column` — 列引用

```
(schema, table, column) = extract_from_column(node)
table_rec = query_table(schema, table)  # Phase 0 已确保存在

if table_rec.source == 'root':
    # 构建 atomic 字段节点
    expression = {"op": "column", "table": f"{schema}.{table}", "column": column}
    hash = sha256(canonical_json(expression))[:16]
    field = UPSERT field(hash, type='atomic', expression)
    # 校验 table_columns 中的 field_hash 一致性
    tc = query_table_column(table_rec.id, column)
    if tc.field_hash and tc.field_hash != hash:
        raise HashMismatch(table, column, tc.field_hash, hash)
    # 回填 field_hash（如新建）
    update_table_column_field_hash(table_rec.id, column, hash)
    return hash

elif table_rec.source == 'middle':
    # 通过表结构查找已有 field_hash
    tc = query_table_column(table_rec.id, column)
    if not tc or not tc.field_hash:
        raise MissingLineageData(f"{schema}.{table}.{column} 缺少血缘数据")
    # 校验 field_hash 对应的 fields 记录存在
    field = query_field(tc.field_hash)
    if not field:
        raise OrphanFieldHash(tc.field_hash)
    return tc.field_hash
```

#### 3.4 `build_expression` — 普通表达式

```
op = map_glot_op_to_internal(node)  # sqlglot op → 内部 op 名
child_hashes = [build_field(child, context) for child in node.args.values()]

expression = {"op": op, "args": [{"hash": h} for h in child_hashes]}
hash = sha256(canonical_json(expression))[:16]

field = UPSERT field(hash, type='expression' | 'atomic_condition' | 'composite_condition', expression)

# 写入 field_references
for child_hash in child_hashes:
    UPSERT field_references(referenced=child_hash, referrer=hash)

return hash
```

**类型判定** (sqlglot 类 → field_type):

| sqlglot 类 | field_type |
|---|---|
| `Add Sub Mul Div` / `Concat Substring` / `Anonymous`(nvl,trim,get_json_object) / `Case` / `Join` / `Alias` / `Where` / `Having` / `Subquery` / `CurrentTimestamp` / `If` / 聚合+窗口 等 | `expression` |
| `EQ NEQ GT GTE LT LTE In NotIn Like Is` | `atomic_condition` |
| `And Or Not` | `composite_condition` |

#### 3.5 JOIN 处理 — 累积包裹模型

JOIN 包装采用**累积模型**：按 FROM → JOIN 顺序，每个 JOIN 基于上一步已包裹的 hash 再包一层。

**数据结构**:
- `ctx.join_wraps: dict[str, list[str]]` — alias → 按 JOIN 顺序的 on_hash 栈
- `left_aliases: set[str]` — 当前左侧别名集合（INNER 合并，LEFT 不合并）
- `all_aliases: set[str]` — 所有已出现的别名（INNER 时全体包裹）

**累积规则**:

```
build_alias_map(select_ast):
    left_aliases = {FROM alias}
    all_aliases = {FROM alias}

    for each JOIN (join_kind, right_alias, on_hash):
        if INNER:
            for alias in all_aliases:
                join_wraps[alias].append(on_hash)     # 左侧全部包当前 ON
            join_wraps[right_alias] = [on_hash]       # 右侧也包当前 ON
            left_aliases.add(right_alias)             # 合并
            all_aliases.add(right_alias)
        else:  # LEFT
            join_wraps[right_alias] = [on_hash]       # 仅右侧包裹
            all_aliases.add(right_alias)
            # left_aliases 不变
```

**延迟包裹**: `build_alias_map` 只记录 `join_wraps` 栈，不创建字段节点。列引用时 `_maybe_wrap_join(base_hash, alias)` 遍历栈逐层 `JOIN(prev, on_i)`。

**示例 — 3 表连续 INNER JOIN**:

```sql
FROM a INNER JOIN b ON cond1 INNER JOIN c ON cond2
```

| 步骤 | join_wraps |
|---|---|
| FROM a | `a: []` |
| INNER JOIN b ON cond1 | `a: [cond1]`, `b: [cond1]` |
| INNER JOIN c ON cond2 | `a: [cond1, cond2]`, `b: [cond1, cond2]`, `c: [cond2]` |

字段 `a.x` 的引用链: `atomic(a.x) → JOIN(atomic, cond1) → JOIN(above, cond2)`

**LEFT 穿透**:

```sql
FROM a INNER JOIN b ON cond1 LEFT JOIN c ON cond2
```

| 步骤 | join_wraps |
|---|---|
| INNER JOIN b | `a: [cond1]`, `b: [cond1]` |
| LEFT JOIN c | `a: [cond1]`, `b: [cond1]`, `c: [cond2]` |

c 不合并到 left_aliases，后续 JOIN 的左表仍是 {a, b}。
> 每个 JOIN 节点是独立的 field 记录，通过 `args[0].hash` 引用上游。内容寻址保证同一路径自动复用。

#### 3.5.1 函数参数提取 — 通用化

所有函数类节点（`round`/`if`/`cast`/`concat`/`nvl` 及任意 `Anonymous`）通过 `_extract_args` 统一提取参数，不再逐个 `isinstance` 写死：

```
_extract_args(node):
    pos_hashes = []
    named = {}

    # 位置参数：this → args[0], expression → args[1], expressions → args[2:]
    this = node.args.get("this")
    if this is Expression: pos_hashes.append(build_field(this))
    
    expr = node.args.get("expression")
    if expr is Expression: pos_hashes.append(build_field(expr))
    
    for e in (node.args.get("expressions") or []):
        pos_hashes.append(build_field(e))

    # 命名参数：其余 args 中的 Expression → params[key]
    for key, val in node.args.items():
        if key in ("this","expression","expressions"): continue
        if key in ("distinct","spec","safe","coalesce","action","format"): continue  # 内部标记
        if val is DataType: named[key] = val.sql()  # cast 的 to
        elif val is Expression: named[key] = build_field(val)
        elif val is str: named[key] = val
```

生成结构：

```json
// round(trans_at / 100, 2)
{"op": "round", "args": [{"hash": "H_div"}], "params": {"decimals": "H_2"}}

// iif(cond, 'high', 'low')
{"op": "if", "args": [{"hash": "H_cond"}], "params": {"true": "H_high", "false": "H_low"}}

// cast(region_cd AS STRING)
{"op": "cast", "args": [{"hash": "H_col"}], "params": {"to": "STRING"}}

// nvl(a, 'default')
{"op": "nvl", "args": [{"hash": "H_a"}, {"hash": "H_default"}]}
```

op 名映射由 `_type_ops` 字典完成（`type(node).__name__.lower()` → 内部 op 名），不再使用 `isinstance` 链，避免 `exp.Cast.name` 返回列名等陷阱。

#### 3.6 聚合 / 窗口处理

**聚合**: 识别 `AggFunc` 节点 + `Group` 子句

```
build_aggregation(agg_node, group_keys, context):
    inner_hash = build_field(agg_node.this, context)   # 被聚合的字段
    group_key_hashes = [build_field(k, context) for k in group_keys]

    expression = {
        "op": "groupby",
        "args": [{"hash": inner_hash}],
        "group_keys": [{"hash": h} for h in group_key_hashes]
    }
    ...
```

**窗口**: 识别 `Window` 节点

```
build_window(window_node, context):
    inner_hash = build_field(window_node.this, context)

    expression = {
        "op": "window",
        "args": [{"hash": inner_hash}],
        "partition_by": [build_field(p, context) for p in window_node.partition_by],
        "order_by": [build_field(o, context) for o in window_node.order],
        "frame": str(window_node.args.get('spec'))  # ROWS BETWEEN ...
    }
    ...
```

#### 3.7 缓存机制

每种节点构建完成后都走 `canonical_json → sha256` 确定 hash。UPSERT 语义：`INSERT ... ON CONFLICT (hash) DO NOTHING`。如果 hash 已存在则直接返回，不创建新记录。

`BuildContext` 内维护内存级 dict: `{canonical_json_str: field_hash}`，避免同一表达式在单次构建中重复计算。

### Phase 4 — 构建子查询

在字段节点全部构建完成后，构建子查询节点。

#### 4.1 SELECT 子查询

```
build_subquery_select(select_ast, context):
    1. build_alias_map — JOIN 包装链（join_wraps 栈）
    2. WHERE → ctx.pending_where
    3. GROUP BY → ctx.group_keys
    4. HAVING → ctx.pending_having
    5. 投影列 — build_field 时：
       - build_column 层：JOIN + WHERE 自动包裹（列引用层）
       - build_function 层：聚合 func → groupby 包裹
    6. 投影层 — 若 ctx.pending_having，对每个投影列包裹 where（HAVING 去糖后 op 为 where）
    7. 构建 structure（无 where 键）
```

**两层包裹模型**：

```
列引用层:  atomic → JOIN → WHERE(column, where_cond)
投影层:    result → where(result, having_cond)   # HAVING 去糖并入 where
```

| 包裹 | 位置 | 作用 |
|---|---|---|
| JOIN | 列引用层 | 约束值域（右表字段才有意义） |
| WHERE | 列引用层 | 筛选行（仅符合条件的行参与后续计算） |
| groupby | 聚合层 | 分组聚合 |
| where | 投影层 | 筛选分组（HAVING 去糖后 op 为 where，仅符合条件的分组输出） |

> WHERE 不存在于 `structure` 中，而是作为 field 节点在不同层级包裹（HAVING 已去糖并入 where）。语义顺序与 SQL 执行一致：FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT。

#### 4.2 UNION 子查询

```
build_subquery_union(union_ast, context):
    branch_hashes = []
    for branch in union_ast.expressions:
        branch_hash = build_subquery(branch, context)  # 递归，branch 是 select 或嵌套 union
        branch_hashes.append(branch_hash)

    structure = {
        "type": "union",
        "branches": branch_hashes
    }
    hash = sha256(canonical_json(structure))[:16]
    UPSERT subquery(hash, type='union', structure)
    return hash
```

### Phase 5 — 绑定 sink 表

```
if sink_table is provided:
    table = query_table(sink_table)
    if not table: raise TableNotFound

    sq_hash = build_subquery(select_ast, context)  # Phase 4 产物

    # 5.1 校验投影列数与表结构列数一致
    projection_count = len(select_ast.expressions)
    tc_list = query_table_columns(table.id) ORDER BY ordinal_position
    if projection_count != len(tc_list):
        raise ColumnCountMismatch(projection_count, len(tc_list))

    # 5.2 写入 table_input_subqueries（旧 active → deprecated，新 → active）
    deprecate_active_input_subquery(table.id, reason="新血缘构建")
    INSERT table_input_subqueries(table_id, subquery_hash, status='active')
    UPDATE tables SET input_subquery_hash = sq_hash WHERE id = table.id  # 冗余指针

    # 5.3 写入 table_column_mappings（按 ordinal_position 逐位对应）
    for i, (tc, field_hash) in enumerate(zip(tc_list, field_hashes)):
        # 旧 active → deprecated
        deprecate_active_column_mapping(tc.id, reason="新血缘构建")
        # 新 → active
        INSERT table_column_mappings(table_column_id, field_hash, status='active')
        # 更新冗余指针
        UPDATE table_columns SET field_hash = field_hash WHERE id = tc.id

    > 注意: 映射纯靠 ordinal_position 对齐，projection 列名与表结构列名可以不同。
```

**`deprecate_active_*` 伪代码:**
```
deprecate_active_input_subquery(table_id, reason):
    UPDATE table_input_subqueries
    SET status='deprecated', deprecated_at=now(), deprecated_reason=reason
    WHERE table_id = ? AND status = 'active'

deprecate_active_column_mapping(tc_id, reason):
    UPDATE table_column_mappings
    SET status='deprecated', deprecated_at=now(), deprecated_reason=reason
    WHERE table_column_id = ? AND status = 'active'
```

### Phase 6 — 事务提交

所有 UPSERT 操作在同一事务中执行。Phase 0 校验失败直接拒绝；Phase 1-5 中任何异常触发回滚。

## 4. 核心类结构 (Python)

```python
# lineage_engine/context.py
class BuildContext:
    cache: dict[str, str]               # canonical_json → field_hash
    db: DatabaseSession
    dialect: str

# lineage_engine/parser.py
class SqlParser:
    @staticmethod
    def parse(sql: str, dialect: str = "mysql") -> sqlglot.Expression: ...

# lineage_engine/normalizer.py
class AstNormalizer:
    @staticmethod
    def normalize(ast: sqlglot.Expression) -> sqlglot.Expression: ...
    # 字段补全、CNF、排序、谓词下推、projection下推、in→join、简化

# lineage_engine/field_builder.py
class FieldBuilder:
    def build(self, node, context) -> str: ...           # 主递归
    def build_literal(self, node, context) -> str: ...
    def build_column(self, node, context) -> str: ...
```

## 6. 性能考量

| 场景 | 策略 |
|---|---|
| 首次构建大 SQL (500+ 字段) | 逐节点构建 + 批量 UPSERT (每 100 条 flush 一次) |
| 重复构建 (幂等) | cache 命中率 90%+，大部分节点直接返回已有 hash |
| 大量 field_references | 批量 INSERT ON CONFLICT DO NOTHING |

## 7. 测试驱动开发策略

引擎开发以**渐进式 SQL 用例集**驱动，从简单到复杂逐层逼近最终效果。

### 7.1 测试层级

```
Layer 0: 单表无变换
    SELECT a, b FROM t
    → 验证: atomic 字段节点正确创建

Layer 1: 单表简单表达式
    SELECT a + b, nvl(c, 0) FROM t
    → 验证: expression 字段节点 + field_references

Layer 2: 单表聚合
    SELECT dept, sum(salary) FROM t GROUP BY dept
    → 验证: groupby 表达式

Layer 3: 两表 LEFT JOIN
    SELECT a.x, b.y FROM a LEFT JOIN b ON a.id = b.id
    → 验证: JOIN 表达式 + 左表字段不包裹 JOIN

Layer 4: 子查询
    SELECT x FROM (SELECT a AS x FROM t)
    → 验证: 子查询节点 + 字段引用链

Layer 5: 多表连续 LEFT JOIN
    SELECT a.x, b.y, c.z FROM a LEFT JOIN b ON ... LEFT JOIN c ON ...
    → 验证: 链式 JOIN 表达式正确

Layer 6: 条件表达式
    SELECT CASE WHEN a > 0 THEN 'pos' ELSE 'neg' END FROM t
    → 验证: casewhen + atomic_condition

Layer 7: UNION
    SELECT a FROM t1 UNION ALL SELECT a FROM t2
    → 验证: union 子查询节点

Layer 8: 窗口函数
    SELECT sum(x) OVER (PARTITION BY dept ORDER BY dt) FROM t
    → 验证: window 表达式

Layer 9: 带 sink 表写入
    SELECT a, b FROM t → sink table
    → 验证: ordinal_position 校验 + table_input_subqueries + table_column_mappings

Layer 10: 违规校验
    SELECT ... LIMIT 10
    SELECT ... FROM a INNER JOIN b INNER JOIN c ON ...
    → 验证: Phase 0 正确拒绝
```

### 7.2 每个 Layer 的验证点

| 验证维度 | 检查内容 |
|---|---|
| 节点正确性 | field_type / expression / hash 是否符合预期 |
| 边正确性 | field_references 是否完整、无遗漏、无多余 |
| 幂等性 | 同一 SQL 跑两次，不创建重复节点 |
| 复用性 | 不同 SQL 共用同一表达式，hash 一致 |

### 7.3 开发流程

```
1. 选一个 Layer 的 SQL 用例
2. 写测试 (pytest): 给定 SQL + schema → 期望的 nodes + edges
3. 实现 → 跑测试 → 修复
4. 测试通过 → 进入下一个 Layer
5. 每 3 个 Layer 做一次重构，保持代码干净
```
